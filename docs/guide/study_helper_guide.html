Part 1 — The building blocksEvery concept the project uses, from zero

1. Language models (LLMs)

A large language model (LLM) is a program that has read an enormous amount of text and learned one skill: given some text, predict what text comes next. Repeat that prediction word after word and you get answers, explanations, stories — or quiz questions.

Three facts that shape everything else

  1. It works in tokens. Text is cut into small pieces called tokens (roughly a short word or part of a word). Models are measured and limited in tokens: "328 tokens" in a trace means 328 of these pieces were processed.
  2. It has no memory. A model does not remember your previous message. Every call starts from nothing, so the program must send the whole conversation so far each time. Memory is the program's job, not the model's (chapter 13).
  3. It can only produce text. It cannot look things up, run code or save files by itself. To do those things, the program must do them on its behalf (chapter 7).
Why it can be wrong A model predicts plausible text, not checked text. It can state a wrong fact confidently. Small models also follow instructions less reliably than large ones — a theme you will meet again in chapter 24.

2. Running a model locally: Ollama

Most people use language models through a company's website or paid API. This project instead runs an open-source model on your own computer, using a free program called Ollama. Nothing leaves your machine and there is no API key or bill.

  • Ollama downloads models (ollama pull qwen2.5:7b) and runs them in the background.
  • It offers a small local web address, http://localhost:11434, that programs send text to.
  • qwen2.5:7b means: the Qwen 2.5 model, 7 billion parameters. Parameters are the numbers the model learned; more parameters usually means smarter but slower and hungrier for memory. A 7B model needs about 8 GB of RAM.
  • Without a graphics card (GPU), the computer's main processor (CPU) does the work, so one reply can take 10–90 seconds. That is why the project logs how long each call takes.
In this project core/llm.py builds the connection (build_chat_model()). The model name comes from the OLLAMA_MODEL setting in .env. scripts/check_ollama.py checks that Ollama is running, the model is downloaded, and the model can call tools.

3. Messages, prompts and temperature

Chat models do not take one block of text; they take a list of messages, each with a role:

RoleWho wrote itExample
systemThe programmer: standing instructions"You are the Tutor, a friendly study helper..."
humanThe user"what is photosynthesis?"
aiThe model, earlier in the chat"Photosynthesis is how plants..."
toolThe program, reporting a tool's result"Notes on gravity: ..."

The system prompt is the most important message: it is the model's job description. Changing a sentence in it changes the model's behaviour — for example, adding "Always end with a fun fact" made the Tutor do exactly that.

Temperature is a creativity dial between 0 and 1. At 0 the model always picks the most likely next word (predictable, good for decisions and grading); higher values add variety (good for writing different quizzes).

In this project Each agent's system prompt is a Markdown file in agents/prompts/ (tutor.md, quiz_maker.md, ...), read once when the chat starts (core/prompts.py). The system prompt is added on the way out to the model and is not stored in the conversation, so each agent sees only its own instructions. Temperatures: 0.2 by default, 0.4 for the Quiz Maker, 0.0 for the router.

4. LangChain and LangGraph

Two free Python libraries do the heavy lifting:

LibraryWhat it gives usUsed for
LangChainStandard building blocks for talking to models ChatOllama (the model connection), message classes (HumanMessage, AIMessage, ...), the @tool decorator
LangGraphA way to build a program as a flowchart of steps that share data, can pause, and can be saved The router, the agents, handoffs, pausing for questions, checkpointing

A useful way to think about it: LangChain is the bricks, LangGraph is the building plan.

5. Graphs: nodes, edges and state

LangGraph describes a program as a graph — the computer-science word for a flowchart:

  • Nodes are steps. Each node is an ordinary Python function.
  • Edges are arrows saying which step runs next. START and END mark the beginning and end.
  • State is one shared dictionary that every node can read. A node does not pass data directly to the next node; it returns the changes it wants, and LangGraph merges them into the state.
def tutor_node(state):
    reply = ...call the model with state["messages"]...
    return {"messages": [reply]}        # only the CHANGE, not the whole state

builder = StateGraph(ChatState)
builder.add_node("tutor", tutor_node)
builder.add_edge(START, "tutor")
builder.add_edge("tutor", END)
graph = builder.compile()

Three more ideas you will meet

  • Reducer. A rule for merging a change into the state. The messages field uses add_messages, which appends new messages instead of replacing the list. That is how the conversation grows.
  • Conditional edge. An arrow whose destination is chosen at run time by a function that looks at the state — "if a question is pending go to ask_user, otherwise finish".
  • Command. A node can return Command(goto="quiz_maker", update={...}) to change the state and choose the next node in one go.
In this project The state is defined in core/state.py (the conversation, the current quiz, a pending question, and some handoff bookkeeping). The graph is built in core/graph.py; its picture is in chapter 20.

6. What is an agent?

An agent is a language model given a job and a way to act. Where a plain chatbot only answers, an agent can decide to do something — call a tool, ask a question, pass work to another agent — and then carry on.

In this project Two agents. The Tutor (agents/tutor.py) explains topics, presents quizzes and grades answers. The Quiz Maker (agents/quiz_maker.py) writes quizzes using its tool. Each file ends with an AgentSpec: a small record of the agent's name, description, prompt file, node function and tools. agents/registry.py lists all agents in one place.

7. Tools and tool calling

A tool is a normal Python function that the model is allowed to ask for. The crucial point: the model never runs the tool. It replies with a structured request — "please call get_topic_facts with topic = gravity" — and our code runs the function and sends the result back. This back-and-forth is the tool-calling loop.

The model never sees the Python code. It only sees the tool's schema: its name, a description (the function's docstring) and its arguments. That is why tool docstrings must be written clearly — they are instructions to the model.

From a real run of the project:

[quiz_maker] calling qwen2.5:7b (round 1, 4 messages, tools: get_topic_facts)
[quiz_maker] model requested tool get_topic_facts({'topic': 'gravity'})
[tool]       get_topic_facts('gravity'): matched 'gravity', returning 6 facts
[quiz_maker] calling qwen2.5:7b (round 2, 6 messages, tools: get_topic_facts)
[quiz_maker] quiz ready: 3 questions on 'gravity'
In this project The tool is get_topic_facts in tools/topic_facts.py; it looks topics up in tools/data/topic_facts.json (six topics). The loop is call_model() in agents/base.py, with each step numbered in the comments. Safety rules: tool errors go back to the model as text instead of crashing; at most 3 rounds; and a fix for a model quirk where the tool request is written as plain text.

8. Structured output and JSON

JSON is a simple text format for data, readable by both people and programs:

{"reason": "The student is answering the quiz questions.", "agent": "tutor"}

A JSON schema describes what valid JSON must look like (which fields, which types, which allowed values). Ollama's structured output feature takes a schema and forces the model's reply to match it. This turns a chatty model into a reliable decision-maker: the reply cannot wander off into prose.

When structured output cannot be used, the program validates the reply instead. The project uses pydantic, a Python library where you describe the shape of data as a class and it checks every field.

In this project Structured output is used by the router ({"reason", "agent"}), by the Quiz Maker's topic finder ({"topic"}) and to repair broken quiz JSON. The Quiz pydantic class in agents/quiz_maker.py rejects quizzes with missing fields, repeated choices, or an answer letter that has no matching choice.

9. Multi-agent systems

One agent could try to do everything, but its instructions grow long and confusing, and small models follow long instructions poorly. A multi-agent system splits the work among specialists, each with a short, focused prompt and only the tools it needs — like a school with a teacher and an exam writer rather than one person doing both.

Splitting raises three new questions, each answered by a later chapter:

QuestionAnswer
Who handles the user's message?A router (chapter 10)
How does one agent get help from another?Handoffs (chapter 11)
What do the agents know about each other's work?They share one conversation history; every message is labelled with the agent that wrote it

10. Routers

A router reads the user's message and decides which agent should handle it. It is the receptionist of the system. In this project it runs for every new message, so the conversation can switch agents at any moment:

"what is photosynthesis?"            -> tutor
"help me build a quiz on gravity"    -> quiz_maker
"1-B, 2-A, 3-C"                      -> tutor   (grading)

The router itself uses a model. It is shown each agent's description (one sentence saying what the agent is for) plus the latest message, and must answer with structured output naming one agent. The description is therefore written for the router: it should say when to choose the agent and when not to.

In this project core/router.py, with its prompt in agents/prompts/router.md. It never names a specific agent — it reads them all from the registry — so a new agent is routable without editing the router. Every choice appears in the log, e.g. [router] -> tutor (The student is answering the quiz questions.).

11. Handoffs

A handoff is one agent passing control to another in the middle of answering a message. There are two kinds:

  • Call and return — "pause, call another agent, get its output, continue". The caller is pushed onto a return stack (a list of agents waiting to get control back). When the called agent finishes, control goes to whoever is on top of the stack.
  • Transfer — "finish and trigger another". The agent simply names who runs next.

A handoff can carry a task — the text after the | above — so the receiving agent is told exactly what to do rather than having to work it out from the history.

In this project core/handoff.py. Agents only say "hand this to X"; a wrapper around every agent (agent_node()) does the bookkeeping, and stops after 3 handoffs per message so two agents can never pass work back and forth forever. The Tutor calls the Quiz Maker (call and return); the Quiz Maker, when the router picked it directly, transfers to the Tutor to show the quiz.

12. Clarifying questions: pause and resume

Sometimes an agent cannot do its job yet: "make me a quiz" — on what? A good agent asks a clarifying question, pauses, and resumes exactly where it stopped once the user answers.

LangGraph provides this with interrupt(). When a node calls it, the whole run stops in the middle and is saved. Later, the program sends the user's answer with Command(resume=answer), and the run continues. One surprise: on resume, the node that paused runs again from its first line, and this time interrupt() returns the answer instead of stopping. So the pausing node must be cheap and safe to run twice — which is why the project gives pausing its own node, ask_user, separate from the agents.

Who decides to ask? Two styles appear in the project:

AgentWho decidesHow
TutorThe modelWhen a request is vague ("explain it") it replies with the marker line CLARIFY: <question>
Quiz MakerCodeA small model call extracts the topic as {"topic": "..."}; then if not topic: the code asks
In this project core/clarify.py holds the whole flow. When the user answers, the chat sees the conversation is paused and sends Command(resume=...) instead of a new message, so the answer skips the router and goes straight back to the agent that asked.

13. Checkpointing, threads and PostgreSQL

Remember that the model has no memory (chapter 1), and a LangGraph graph forgets its state when a run ends. A checkpointer fixes this: it saves a snapshot of the state (a checkpoint) after every step, so the next run can pick up exactly where the last one stopped — tomorrow, after a reboot, or in the middle of a paused question.

Snapshots are filed under a thread id. One thread is one conversation. Using the same thread id resumes that conversation; a new id starts a fresh one. Different threads never share memory.

The snapshots are stored in PostgreSQL (often "Postgres"), a free, widely used database. Because the conversation is in the database, the chat program only sends the new message to the graph; everything else is loaded from the latest checkpoint.

In this project infra/postgres.py sets up LangGraph's PostgresSaver. Each chat start creates a new thread id such as chat-20261101-135805; python chat.py --list shows saved conversations and --thread <id> resumes one.

14. Docker

Installing a database directly on your computer means user accounts, permissions and a service that runs forever. Docker avoids that: it runs software inside a sealed, disposable box called a container, built from a ready-made image (here, the official postgres:16-alpine image).

  • docker-compose.yml describes the container: which image, the username and password, which port.
  • docker compose up -d starts it in the background; docker compose down -v removes it and all its data.
  • The database's files live in a Docker volume, so conversations survive restarts.
  • The project uses port 5433 rather than Postgres's usual 5432, to avoid clashing with any Postgres already installed.

15. Streaming

A model produces its answer one token at a time. Streaming shows those tokens as they arrive, so the reply appears word by word instead of after a long silence — important when a reply takes a minute.

LangGraph offers two calls: graph.invoke() waits and returns the final result; graph.stream() hands over events while the graph is still running. The chat asks for two kinds:

  • "messages" — each token, labelled with the node that produced it;
  • "updates" — each node's changes, the moment that node finishes.

Not everything should be streamed: the router's JSON and the Quiz Maker's quiz JSON are filtered out by node, and replies that start with HANDOFF: or CLARIFY: are held back by looking at their first few characters before printing anything.

In this project chat.py, in particular run_turn() and the ReplyStreamer class.

16. Tracing with MLflow

When something goes wrong in a multi-agent system, you need to know exactly what happened: which agent ran, what the model was sent, what came back, how long each step took. Tracing records all of this.

  • A trace is the record of one message you sent.
  • It is a tree of spans. Each span is one piece of work (a node, a model call, a tool call) with its inputs, outputs, duration and labels.
  • A session groups the traces of one conversation.

MLflow is a free tool that stores traces (here in one file, mlflow.db) and shows them in a web page. A trace for a quiz request looks like this:

chat_turn                         your message, the replies, the whole conversation
└── LangGraph
    ├── router
    │   └── route                 chosen agent + reason
    │       └── ChatOllama        the model call
    ├── quiz_maker
    │   ├── quiz_maker:find_topic     topic: "gravity"
    │   ├── agent:quiz_maker
    │   │   ├── ChatOllama            the model asks for the tool
    │   │   ├── tool:get_topic_facts  input: topic  -> output: the notes
    │   │   └── ChatOllama            the model writes the quiz
    │   └── handoff:quiz_maker->tutor
    └── tutor                     presents the quiz (no model call)

Most spans are recorded automatically (mlflow.langchain.autolog() hooks into LangChain and LangGraph). The project adds its own spans where it wants clearer labels — above all, which agent did the work.

In this project infra/tracing.py. View traces with mlflow ui --backend-store-uri sqlite:///mlflow.db --port 5000, then open http://127.0.0.1:5000 → study-helper → Traces (or Sessions).

18. What the Study Helper does

The Study Helper is a terminal chat with two agents:

  • The Tutor answers study questions, presents quizzes and grades your answers.
  • The Quiz Maker writes short multiple-choice quizzes, using study notes from its get_topic_facts tool.
You typeWhat happens
what is photosynthesis?Router → Tutor explains
help me build a quiz on gravityRouter → Quiz Maker finds the topic → calls the tool → writes the quiz → hands to the Tutor, which shows the questions
1-B, 2-A, 3-CRouter → Tutor grades against the hidden answer key
make it harderRouter → Quiz Maker writes a harder quiz on the same topic
make me a quiz (new chat)Quiz Maker asks "Which topic?" and pauses until you answer
explain it (new chat)Tutor asks which topic and pauses

Every conversation is saved in Postgres, every message is traced in MLflow, and replies stream word by word.

21. One message, start to finish

A real run. The conversation so far: you asked "what is photosynthesis?" and the Tutor answered. Now you type help me build a quiz on gravity.

#StepWhat happens
1Input
chat.py		The chat reads your line. Is the conversation paused on a question? No — so it becomes a new message.
2Trace opens
infra/tracing.py		A chat_turn span starts. Everything until the reply becomes one trace.
3Checkpoint loaded
infra/postgres.py		LangGraph loads the thread's latest snapshot (2 messages) and appends yours. Snapshot saved.
4Router
core/router.py		The model reads the agent descriptions and your message:
[router] -> quiz_maker (The student requested help in building a quiz...)
5Find the topic
agents/quiz_maker.py		A small structured call returns {"topic": "gravity"}. A topic exists, so no question is asked.
[quiz_maker] topic: 'gravity'
6Tool loop
agents/base.py		Round 1: the model requests get_topic_facts('gravity'); our code runs it; 6 facts go back. Round 2: the model writes the quiz as JSON.
7Check & storepydantic validates the JSON. The quiz (with answers) goes into state["quiz"], not into the chat. Chat message: "I made a 3-question quiz on gravity."
8Handoff
core/handoff.py		Nobody called the Quiz Maker, so it transfers to the Tutor.
[handoff] quiz_maker -> tutor (transfer)
9Tutor presents
agents/tutor.py		Plain Python formats the questions (no model call, no answers shown) and marks the quiz as presented. "Where next?" → END. Final snapshot saved.
10Output
chat.py		The stream delivers each node's message as it finishes: the Quiz Maker's note, then the Tutor's quiz.
11Trace closesThe chat_turn span records the replies, the agents involved and the whole conversation. MLflow saves the trace.

Then you answer 1-B, 2-A, 3-C: the router picks the Tutor, which recognises quiz answers and grades them against the stored key in Python, in under a millisecond — [tutor] graded the quiz in code: 2/3.

Where the time goes In that run, finding the topic took 22 s, the tool request 59 s and writing the quiz 83 s, plus the router. The project's own code took a few milliseconds. On a CPU, almost all the waiting is the model.

22. A clarifying question, start to finish

A new conversation, with no topic given:

  1. You: make me a quiz. The router picks the Quiz Maker. find_topic() returns an empty topic.
  2. Code decides to ask. The Quiz Maker returns the question and sets pending_question in the state.
  3. "Where next?" sees the pending question and goes to ask_user.
  4. Pause. ask_user calls interrupt(). The run stops and is saved in Postgres. The chat prints quiz_maker asks: Which topic would you like the quiz to be about? You could quit now and come back later.
  5. You: volcanoes. The chat sees the conversation is paused, so it sends Command(resume="volcanoes"). The router is skipped.
  6. Resume. ask_user runs again; interrupt() now returns "volcanoes". It adds your answer to the conversation and sends control back to the Quiz Maker.
  7. Carry on. find_topic() now finds "volcanoes". The tool has no notes on volcanoes and says so, so the model writes basic questions from its own knowledge. The rest is the same as chapter 21, steps 7–11.

In MLflow this shows as two traces: the paused one, and the one for your answer, which contains a clarification span with the question and your answer.

24. What the model does, what code does

The most useful lesson from building this project: let the model do the language, and let code do the bookkeeping. Everything that needs understanding the student is done by a model. Jobs with one exact right answer are done by Python, because a small model gets them wrong surprisingly often.

JobDone byWhy
Choosing the agent for each messageModel (router)Needs to understand what you mean
Explaining a topicModel (Tutor)Language
Reading the quiz topic from your sentenceModel (structured)Needs understanding; the JSON shape keeps it on track
Calling the tool and writing questionsModel (Quiz Maker)Language
Is the topic missing?CodeThe model kept asking "which topic?" even when told
Showing the quizCodeInstant, and cannot reveal answers
Grading "1-B, 2-A, 3-C"CodeThe model once marked a wrong answer right, and took 143 s
Removing stray "A)" letters from choicesCodeThe prompt said "no letters"; the model added them anyway

27. Adding a third agent

Because the router, the graph and the handoff code read everything from the registry, a new agent needs only three things:

  1. agents/flashcards.py — a node function and an AgentSpec: 
    from agents.base import AgentSpec, run_agent

def flashcards_node(state):
    return run_agent(AGENT, state)

AGENT = AgentSpec(
    name="flashcards",
    description="Makes flashcards for memorising facts. Choose it when the "
                "student asks for flashcards or help memorising.",
    prompt_file="flashcards.md",
    node=flashcards_node,
)
  2. agents/prompts/flashcards.md — its system prompt.
  3. One line in agents/registry.py — add flashcards.AGENT to the list.

The router can now choose it, the Tutor can hand work to it, it gets its own colour in the chat, and checkpointing and tracing cover it automatically.

pydanticPython library that checks data against a declared shape.
ReducerRule for merging a node's change into the state (e.g. append messages).
RegistryThe single list of all agents (agents/registry.py).
Return stackThe list of agents waiting to get control back after calling another.
RouterThe step that chooses which agent handles each new message.
SessionIn MLflow, the group of traces from one conversation.
SpanOne piece of work inside a trace, with inputs, outputs and timing.
StateThe shared dictionary that flows through the graph.
StreamingShowing a reply token by token as it is generated.
Structured outputForcing a model's reply to match a JSON schema.
System promptThe hidden first message giving a model its instructions.
TemperatureHow varied (high) or predictable (low) the model's wording is.
ThreadOne saved conversation, identified by a thread id.
TokenA small piece of text (about a word or part of one) that models read and write.
Tool / tool callingA function a model may request / the loop where code runs it and returns the result.
TraceThe full record of one message: a tree of spans.
TransferA handoff where nobody waits for control to come back.
